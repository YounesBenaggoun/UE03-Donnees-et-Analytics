Dockerfile multi-étapes

Image minimale node:20-alpine, exécution sous utilisateur non-root appuser.

# Étape 1 : Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

# Étape 2 : Runtime
FROM node:20-alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package.json ./
USER appuser
EXPOSE 3000
CMD ["node", "dist/index.js"]

Partie B · Collecte de Logs

B1. Centralisation en direct

Stack Loki + Promtail (ou Grafana Alloy). Labels choisis pour limiter la cardinalité :

  • job="croakedup" (statique)
  • level (info, warn, error)
  • build (ex: beta-20260926-5)
  • map (harbor, vault, etc.)

Justification : on évite les labels à forte cardinalité comme player_id ou match_id qui exploseraient l'index. Ces informations restent dans le corps du log JSON.

B2. Ingestion de l'export historique

Le fichier admin-export-2026-09-20_26.log est brut. Pièges identifiés :

  • Format : JSON lines non standard, certains objets multi-lignes.
  • Horodatage : timestamps en millisecondes (epoch) et dates lisibles.
  • Fuseau : mélange de UTC et heure locale (ex: "12:04:13 AM").
  • Qualité : doublons (ex: k5qHKRUYB apparaît deux fois), trous temporels, champs manquants (rttMs absent pour certains rapports réseau).

Script Python de parsing et normalisation (extrait) :

import json, re
from datetime import datetime, timezone

def parse_line(line):
    # Extraction de l'entête et du JSON
    match = re.match(r'^(.*?) · (.*)$', line)
    if not match: return None
    meta, payload = match.groups()
    # Normalisation de la date
    try:
        dt = datetime.fromisoformat(meta.split(' · ')[-1])
    except:
        dt = datetime.fromtimestamp(int(meta.split()[-1])/1000, tz=timezone.utc)
    return {"timestamp": dt.isoformat(), "meta": meta, "data": json.loads(payload)}

C3. Métriques vs Logs

Métriques

  • Agrégations numériques (latence, taux d'erreur)
  • Alerting sur seuils
  • Faible cardinalité
  • Coût stockage optimisé

Logs

  • Contexte riche (stacktrace, IDs)
  • Debug et postmortem
  • Haute cardinalité acceptable
  • Recherche full-text

Partie D · Tableaux de Bord

Dashboards provisionnés en JSON dans grafana/dashboards/ :

  • Santé du service : "Le service répond-il correctement ?" (QPS, latence p95, taux d'erreur 5xx)
  • Performance côté joueur : "Les joueurs subissent-ils des saccades ?" (frameMs, fps, rttMs par build/map)
  • Activité de jeu : "Les parties se déroulent-elles normalement ?" (parties/jour, score moyen, durée)

Chaque panneau a une question en titre. Exemple : "Quel est le taux de rapports 'frame' par build ?"

E2. Comportements anormaux

Dégradation liée à une version

Le build beta-20260926-5 présente 3x plus de rapports frame que beta-20260924-3.

sum by (build) (count_over_time({job="croakedup"} |= "Performance spike" | json | cause="frame" [1h]))

Population touchée

Les joueurs sur Safari et Firefox sont sur-représentés (80% des rapports).

Parties suspectes

La partie Ju73lcJQS a un score final 1-3 mais 47 rapports de performance en 10 minutes.

Données falsifiées

Un client envoie des frameMs négatifs (render: -47.2) → incohérence.

E3. Règles d'alerte

groups:
  - name: croakedup_alerts
    rules:
      - alert: TauxRapportsFrameEleve
        expr: rate(game_reports_total{cause="frame"}[5m]) > 10
        for: 2m
        labels: { severity: critical }
        annotations: { summary: "Taux de saccades anormal" }
      - alert: BuildDegrade
        expr: sum by (build) (rate(game_reports_total{cause="frame"}[1h])) > 3 * sum by (build) (rate(game_reports_total{cause="frame"}[1h] offset 1d))
        for: 10m
        labels: { severity: warning }

Faux positifs : pics légitimes lors de tests de charge. Faux négatifs : dégradation lente non détectée par seuil fixe → utiliser des tendances.

Partie F · Rapport d'Incident (Postmortem)

Question 1 : « Des joueurs se plaignent de saccades depuis jeudi soir. Pourquoi, et qui est touché ? »

Chronologie : Jeudi 26/09 à 22:00, déploiement du build beta-20260926-5. À partir de 22:15, explosion des rapports frame (frameMs > 300ms).

Cause : Régression dans le pipeline de rendu (renderOverlay +400ms).

Population : 78% des joueurs sur Safari/Firefox, GPU Apple M2. Les joueurs sur Chrome/Windows sont épargnés.

Preuves :

-- Requête Loki {job="croakedup"} |= "Performance spike" | json | cause="frame" | line_format "{{.build}} {{.browser}} {{.frameMs}}"

Actions correctives : Rollback vers beta-20260924-3, correctif sur le rendu des overlays.

Actions préventives : Ajout d'un test de performance dans la CI, alerte sur dégradation inter-build.

Question 2 : « Est-ce que quelqu'un abuse du jeu ? »

Détection : La partie Ju73lcJQS présente un comportement anormal : 47 rapports de performance en 10 minutes, score final 1-3, mais des frameMs négatifs et des rttMs incohérents.

Signature : Client Safari sur Mac M2, build beta-20260926-5, envoie des rapports falsifiés (render négatif).

Preuves :

-- Requête Loki {job="croakedup"} |= "Ju73lcJQS" | json | render < 0

Actions : Bannissement temporaire du client, validation des rapports côté serveur (rejet des valeurs négatives).
